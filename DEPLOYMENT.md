# Deploying ResumeMaxxer to Vercel

Everything runs in **one Vercel project**: the frontend, the auth service, the
API and the LaTeX compiler. One domain, one deployment, one set of environment
variables.

`vercel.json` is the source of truth for the wiring. JSON has no comments, so
the reasoning lives here.

---

## 1. The shape

Vercel Services lets one project hold several independently built units, routed
by path.

```
                      one domain
                          |
        +-----------------+------------------+
        |                 |                  |
  /api/auth/*          /api/*               /*
   auth service       FastAPI API        React frontend
  (auth-server/)      (backend/)         (frontend/)
                          |
                     service binding
                          |
                    LaTeX compiler
                      (latex/)
                   no public route
```

Two things about this are load-bearing:

**The order of the rewrites matters.** `/api/auth/(.*)` must come before
`/api/(.*)`, because Vercel takes the first match. Reverse them and every
sign-in request goes to FastAPI, which has no such route, and the failure looks
like a broken auth service rather than a routing mistake.

**Routing into a service is final.** If a path matches `/api/(.*)` and FastAPI
has no route for it, Vercel returns FastAPI's 404 - it does not fall through to
the frontend. That is why `/health` needs its own rewrite.

**The LaTeX service has no rewrite at all**, which is what keeps it off the
public internet. The API reaches it through a *service binding*, which both
grants the access and injects the internal URL as `LATEX_API_URL`. Nobody can
reach the compiler except the API, and no hostname is hardcoded anywhere.

### Why one domain rather than four projects

Same-origin is not a tidiness preference here. The Better Auth session lives in
a cookie. Served from one domain, it is a first-party cookie and simply works.
Split across `app.example.com` and `auth.example.com`, it becomes a third-party
cookie in a cross-site request - which Safari blocks outright and Chrome is
progressively restricting. Every CORS rule in this codebase also becomes dead
weight the moment the three services share an origin.

## 2. What runs where

| Service | Runtime | Entry point | Notes |
|---|---|---|---|
| `web` | Vite static build | auto-detected | `frontend/`, built to `dist/` |
| `auth` | Node / Express | `src/index.ts` | zero-config: Vercel detects the Express app |
| `api` | Python 3.12 / ASGI | `main:app` | `backend/main.py` already exposes `app` |
| `latex` | container | `Dockerfile.vercel` | built to an OCI image, kept internal |

Measured limits, against the ones that actually bind:

| Limit | Ceiling | This app |
|---|---|---|
| Python bundle, uncompressed | 500 MB | ~95 MB for a clean `requirements.txt` |
| Max function duration (Hobby) | 300 s | LaTeX timeout is 180 s, tailoring ~10 s warm |
| Request / response body | 4.5 MB | JD upload capped at 4 MB |
| Memory (Hobby) | 2 GB | well under |

> **Do not raise the upload cap above 4 MB.** Vercel rejects a request body
> over 4.5 MB before our code runs, with a bare platform 413. The app's own
> limit sits under that deliberately, so every rejection is ours and carries
> the message that actually helps - "this looks like a scanned PDF". It was
> 5 MB before this deployment work, which would have put uploads in the
> 4.5-5 MB band into the platform's hands.

## 3. The LaTeX cold-start problem, and the fix

Tectonic downloads the TeX packages a document needs on first use. Locally,
`docker-compose.yml` persists them in a named volume: first compile ~110 s,
every one after ~1.3 s.

A Vercel container has **no persistent volume** and **scales to zero after five
minutes idle**. Left alone, every cold start would re-download the tree and some
student would wait nearly two minutes for a PDF.

So the cache is baked into the image at build time. `latex/Dockerfile.vercel`
compiles `latex/warmup.tex` during the build, and the packages land in an image
layer.

For that to work the warm-up has to pull the same packages a real resume pulls,
so `latex/warmup.tex` **is** a real resume, generated by the real renderer:

```bash
cd backend && python generate_latex_warmup.py
```

`backend/tests/test_latex_warmup.py` fails if the committed file drifts from
`latex_renderer.PREAMBLE`, so a preamble change cannot silently ship a useless
cache.

Measured locally on a freshly built image:

| | Time |
|---|---|
| First compile, cold container | **1.19 s** |
| Second compile | 0.95 s |
| A document the cache never saw, cold container | **1.01 s** |

Baked cache: 43.5 MB, 311 files.

### If the container misbehaves

Two things to know if it ever needs debugging:

- Upstream reads `process.env.Port` — capital P, lowercase rest. Environment
  variables are case-sensitive on Linux, so plain `PORT` does not move it. The
  Dockerfile pins both spellings.
- The warm-up runs as root and Tectonic caches into `$HOME/.cache/Tectonic`.
  Adding a `USER` directive to that Dockerfile would put the runtime cache
  somewhere else and silently undo the whole thing.

## 4. First deploy, step by step

### 4.1 Check the two gated features

`vercel.json` uses **Services** and **Container Images**, both of which show a
"Permissions Required" banner in Vercel's docs. Confirm they are available on
your account before the first deploy — if they are not, the build fails on the
config rather than on the code.

### 4.2 Import the repo

[vercel.com/new](https://vercel.com/new) → import
`aprameyatatachari/ResumeMaxxer`. Framework preset **Other**, root directory the
repository root. Do not set a build command; each service defines its own.

### 4.3 Turn on system environment variables

Project **Settings → Environment Variables → Enable access to System
Environment Variables**.

This is not optional. Without it, `VERCEL`, `VERCEL_ENV` and
`VERCEL_PROJECT_PRODUCTION_URL` are absent, so the database pool sizing cannot
tell it is serverless and the two services cannot agree on the JWT issuer
without you setting `BETTER_AUTH_URL` by hand.

### 4.4 Set the variables

| Variable | Value | Why |
|---|---|---|
| `DATABASE_URL` | Neon **pooled** string (host contains `-pooler`) | the direct endpoint runs out of connections under serverless load |
| `BETTER_AUTH_SECRET` | `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` | signs session cookies; must differ from your local value |
| `BETTER_AUTH_URL` | `https://your-domain` | the JWT `iss`/`aud`; both services must agree |
| `ENVIRONMENT` | `production` | hides `/docs` and skips `create_all` on boot |
| `GEMINI_API_KEY` | your AI Studio key | funds the free weekly allowance only |
| `GEMINI_MODEL` | `gemini-2.0-flash` | |
| `LATEX_API_KEY` | any long random string | must match `API_KEY` on the `latex` service |
| `PORT` | `3000` | tells Vercel which port the LaTeX container listens on |
| `GITHUB_TOKEN` | optional fine-grained token, public read | lifts the GitHub API limit from 60/hr to 5,000/hr |

Do **not** set `LATEX_API_URL`. Vercel injects it from the service binding;
setting it by hand would override the binding and send resume content to
whatever you typed.

### 4.5 Pick the region

Default is `iad1` (Virginia). Your Neon instance is in **`ap-southeast-1`
(Singapore)**, so set the function region to **`sin1`**. Left on the default,
every query crosses the planet twice, and the tailoring endpoint makes several
in sequence.

### 4.6 Create the schema

Nothing creates tables automatically in production, on purpose: many instances
starting at once, all racing to issue DDL, is a good way to deadlock a fresh
database. Run both from your laptop, pointed at the production database:

```bash
cd auth-server && npm run migrate
```

```bash
cd backend && DATABASE_URL="<the production URL>" python migrate.py
```

The first creates Better Auth's tables (`user`, `session`, `account`,
`verification`, `jwks`); the second creates the API's tables and adds any
column the models have gained since the database was last touched. Both are
idempotent, and `migrate.py` re-reads the schema afterwards to prove every
modelled column really exists rather than assuming it.

**Run `migrate.py` on every deploy that changes a model, not just the first
one.** `create_all` alone does not add columns to a table that already exists,
and this project has been broken by that twice — most recently while adding the
quota columns, where an otherwise clean deploy 500ed every authenticated
endpoint with `column users.free_runs_used does not exist`. `migrate.py` now
handles additive column changes; anything destructive (dropping, renaming,
retyping) it reports and refuses, which is the point at which the project needs
Alembic. See "Known gaps" in ARCHITECTURE.md.

### 4.7 Deploy and verify

```bash
git push
```

Then, against the deployed domain:

1. `GET /health` → `{"status":"ok","database":"ok"}`
2. `GET /api/auth/jwks` → a JSON key set (proves the auth service is routed)
3. Sign up, add one vault entry, tailor a resume → proves all four services and
   the binding
4. `GET /docs` → 404, confirming `ENVIRONMENT=production` took effect

## 5. Local development is unchanged

`start.bat` still runs the three services on their own ports with
`docker compose` for LaTeX, and `stop.bat` still frees them. None of the Vercel
configuration affects local work:

- `frontend/.env.local` keeps the absolute localhost URLs
- `frontend/.env.production` (empty values) only applies to a production build
- `docker-compose.yml` runs the upstream image directly; `Dockerfile.vercel` is
  only used by Vercel

To exercise the deployed routing locally, `vercel dev` runs all four services
together with the same rewrites — it needs Docker running for the LaTeX
container.
